# 黑翼多人性能与攻击播放修复方案

状态：本方案的 A–C 核心优化已实施；结果、参数差异及尚未完成的实机验收见[实施结果](D:/mcmodtest/AcademyCraft-Reborn-26.2/docs/vfx/black_wings/multiplayer_optimization_result.md)。日期：2026-09-07。下文保留实施前的诊断与建议。

排查基于 `08e63fbf6b5234e4b83accea8f6ce91ba72bcbb2` 的当前工作区，Minecraft 26.2.0 / NeoForge 26.2.0.70。
工作区已有伤害、CP 回复等其他修改，本轮未改动这些文件，也未创建 Git 提交。

## 1. 结论与范围

建议采用“可靠的攻击事件 + 客户端独立播放时间线 + 共享采样/复用网格缓冲 + 按可见程度分配渲染预算”。先交付播放与 CPU 渲染修复，再验证飞行控制降频；GPU 参数化形变作为后续性能门槛未达标时的升级路径。

现有黑翼已经在客户端生成几何，服务器没有逐帧发送翅膀模型。排查确认的两个主要问题是：客户端直接用世界 tick 判断攻击是否结束，迟到事件存在完全不播放的路径；单个黑翼的曲线采样、管网格生成和缓冲上传成本很高，多人同时出现会叠加。当前还没有实机网络抓包，不能把全部卡顿直接归因于带宽不足。

本轮修复必须保留以下已确认效果：

- 肩胛喷出的弯曲墨黑龙卷，少量深紫色，细而流动的亮紫高光，位置缓慢波动的小镂空。
- 近景左侧 14 条、右侧 10 条高光及现有宽度；核心先画、高光后画的稳定顺序。
- 双翼向下抽打 → 左翼侧抽 → 右翼侧抽 → 压缩突刺 → 四翼砸地的轮换顺序。
- 正常运行每招 0.8 秒，服务端间隔 16 tick；蓄势约 20%，蓄势末尾与挥动重叠，保持连续回收。
- 四翼以施放位置为中心，落在 12 × 12 米正方形的四角，各角独立落地；角色后续转身不移动已确定的落点。
- 服务端判定技能启用、费用、冷却和伤害。现有伤害仍是即时扇形判定，五种视觉动作没有独立伤害区域；本轮不顺带改为延迟命中或四个伤害圈。
- 编辑器与游戏使用相同的采样和材质路径。性能优化不另做一套只供预览的替代动画。

## 4. 攻击事件与连续播放

### 4.1 事件结构与服务器职责

保留“一次接受攻击，一次广播”架构。建议事件包含：实体 ID、激活周期 `activationEpoch`、该周期内递增 `sequence`、招式 ID、服务器起始 tick、固定世界落点。实体 ID 只负责查找，周期与序号防止关闭重开、实体 ID 复用和重复事件误播放。

攻击接受、扣费、轮换、16 tick 间隔与现有伤害仍在服务器原入口执行。客户端不能指定最终招式、目标或伤害。相同事件不因重试重复扣费、重复命中或重复播放。不增加每 tick 动画进度包，也不为视觉新增高频校时包。

启动、停止、开始追踪实体时同步黑翼激活周期和必要的当前状态快照；停用与黑转白显式取消该周期动画。迟加入观察者只接收当前有效状态，不补播该玩家的历史攻击。格式变化必须同步更新客户端/服务器协议版本或能力协商，不能让旧 codec 静默读取新字段。

### 4.2 客户端播放时钟

新增独立的、可单测的事件播放时间线，实体与 Minecraft API 接入留在 `WingVfx`。

- 收包只校验和入队，不创建网格。第一次实际提交该攻击画面时建立本地播放起点；尚未开始绘制的事件不会被“服务器起始 tick 已过去 16 tick”直接清掉。
- 动作进度来自客户端单调时钟，正常每次完整播放 0.8 秒；游戏暂停时冻结，世界时间校正不改变已经开始的进度。墨流、高光和动作使用明确的同一视觉时基，避免一部分按世界 tick、一部分按渲染 dt 发生相位跳变。
- 服务端 tick 保留用于排序辅助、状态快照与诊断，不直接作为客户端动作到期时间；RTT/2 不是可靠的单向延迟，跨端 tick 差也不能直接记成网络耗时。
- 收到重复序号直接忽略。收到下一招时当前动作正常收回，再开始下一招；每实体最多“当前一招 + 最新待播一招”，待播更新时合并较旧事件，并记录合并原因。正常 0.8 秒间隔及合理抖动下应完整保持轮换。
- 实体或激活附件尚未就绪时暂存，建议默认最多 500 ms，并限制实体条目数；成功匹配激活周期才播放。解除追踪、死亡、停用、切维度、断线、黑转白均清理相关状态。
- 待播事件超过 1 秒仍不能开始时丢弃旧待播并请求/等待轻量状态恢复，不能积累几秒钟历史动作。多个包在同一帧集中处理时只保留最新有效待播。

正常帧率下不通过定期网络包校正每帧进度，也不缩短蓄势来追包。发生超过 250 ms 的本地渲染中断时，不保证中断期间存在可见画面：恢复后合并旧事件，以约 80 ms 的短过渡回到当前有效姿态；最新尚未播放事件仍可正常开始。不能为了补完每个历史动作而无限延迟，也不能为了维持墙钟 0.8 秒把所有未播放事件直接删光。以上退化阈值是初始参数，需在抖动测试中调定。

### 4.3 本机输入延迟的单独处理

第一批播放修复仍以服务器接受事件为起点，因此网络 RTT 引起的“点击到开始”延迟仍存在，只是事件开始后会连续播放。先测量这一延迟，再决定是否启用本机视觉预测。

若常用联机条件下仍明显迟钝，第二阶段加入可关闭的本机预测：点击后预播本地候选动作，服务端返回确认后绑定同一请求 ID，不从头重播；拒绝时短时间收回，并校正下一招。预测只改变画面，不预扣服务器费用或施加伤害。高延迟下错误预测可能表现为一次无伤害挥动，应计数并可回退到确认后播放。

现有左键由 `MixinMinecraft` → `PlayerLeftClickSwingPacket` 统一分派，其他技能也使用该入口。预测需给这条请求加入关联 ID 或建立等价的单次路由，不能同时从通用左键包和新专用包触发两次黑翼攻击。不得把完整蓄势停在确认点等待回包，否则会重新引入用户已要求去除的停顿。

## 5. CPU、网格与内存优化

### 5.1 分支采样缓存

对每个分支、当前时间和攻击进度，一次构建轴向采样表，保存主轴位置、切线/运输旋转、半径与宽度包络。核心和 18 条细流共用这些结果；只把各自的相位、轨道半径和颜色留给细流计算。

`VortexJetGeometry` 在半径分量为零时的主轴与细流相位无关，可直接抽取主轴求值，避免为主轴做完整轨道三角运算。现有 `buildWhip` 已有分段结果，要复用它，不再按每条细流重复准备主轴。高光与墨屑的非网格 u 用插值获取主轴/旋转，四元数插值注意方向连续与归一化；必要时提高局部采样密度。

预计算每条细流的固定随机参数；复用浮点数组、向量和临时对象。公开采样能力置于 `org.academy.api.client.render.vfxgraph` 下，避免依赖玩家类，保留其他实体和编辑器调用能力。缓存按实体/分支隔离，仅保留当前所需容量，目标、LOD、形变参数、资源重载变化时正确失效。

### 5.2 直接生成合并网格

提供可写入调用方缓冲的管网格构建接口，先统计所需大小，然后直接写入复用的顶点/索引缓冲；旧 `build` 包装接口暂时保留兼容调用。去掉每条曲线一个直接缓冲、再整体复制一次的路径。环截面 sin/cos 表按圆周精度缓存，切线运输不用每环新建数组。

容量按档位增长并设置总上限，稳定场景达到容量后不再按帧分配大型直接缓冲。资源重载/关闭时释放 GPU 对象；缓冲复用必须区分当前正在使用的帧，不能覆盖尚在 GPU 队列中读取的内容。

第一批保留现有镂空的独立 run 拓扑，直接复用索引写入缓冲；不做按时间无限增长的索引缓存。相同拓扑可复用索引，但移动镂空会改变拓扑，必须重建受影响部分。只有后续改用稳定拓扑和显式孔洞遮罩时，才能把完整索引永久静态化。

绘制顺序沿用稳定核心→细流→高光，不恢复交换删除，也不盲目按材质排序而让黑色主体覆盖左侧亮带。跨实体透明排序需独立检查，不能仅为减少已很少的 draw call 把所有玩家随意合成一批。

### 5.3 正确剔除与生命周期

将“维护播放时间”和“求几何/绘制”分开。先根据效果包围范围判定可见性和预算，再执行昂贵采样。此优化先让黑翼/解析式无历史依赖效果接入，不把通用有历史粒子模拟直接停掉。

待机包围范围包含左右全部风暴；攻击包围范围包含肩根、挥动路径、高空控制点和固定落点，并带管径余量。不能只使用角色身体 AABB 或固定 8 米球。通过角色追踪与插值姿态维护肩根，即使身体在画面外，只要翼尖/攻击进入画面仍可绘制。

短暂离开视野保留约 0.75 秒轻量状态，跳过几何工作，重入时直接用当前进度恢复；长时间不可见释放大缓冲。播放状态不依赖某一帧是否采到了角色根矩阵。解除追踪、停用、世界清理立即回收，不靠超时留下幽灵翅膀。

## 6. LOD 与多人总预算

LOD 以屏幕投影大小为主，距离作为初始分档，并加入约 15% 滞回和 100 ms 过渡。目标受攻击者和近处攻击提高优先级；细节减少不能改变方向、抽打轨迹、四个落点或动作速度。以下数量为初始调试档位，实施后需用截图和计数验证，不是已达成结果。

| 档位 | 建议适用情况 | 每侧细流 / 轴向段 / 圆周段 | 高光与墨屑 |
| --- | --- | --- | --- |
| 本机/特写 | 本机黑翼、编辑器高质量对照 | 18 / 100 / 8，保留当前近景 | 左 14、右 10 条高光；每侧 24 墨屑 |
| 近处 | 大投影远端角色，初始约 0–16 m | 12 / 64 / 6 | 保留亮带宽度与左右覆盖比例；墨屑降至 12 |
| 中距 | 初始约 16–40 m | 8 / 40 / 4 | 保留代表性细亮带；墨屑 4–6 |
| 远处 | 初始约 40–80 m | 4 / 24 / 3 | 少量可见高光；墨屑 0 |
| 极远/遮挡外 | 小投影或离开视锥 | 跳过待机几何；相关可见攻击保留最简主轴 | 不因角色中心距离大就切掉已进入画面的攻击 |

当前节点对 `segments` 下限为 24、`filaments` 下限为 3，初始档位可覆盖这些约束；新增动态 LOD 参数必须保持旧 JSON 默认不变。每个 LOD 选择稳定的细流子集，保留穿过镂空的桥接线。LOD 变化不重新随机选线或从零启动高光。

增加每帧跨实体预算，至少统计曲线数、采样点、生成顶点、上传字节、CPU 时间。建议默认初始上限为黑翼合计 120,000 顶点、8 MiB 上传/帧，两者同时约束；本机完整效果预留份额，四翼仍计入同一份预算，远端按优先级降档。该数值用于建立可调试的硬边界，最终根据实测调整，不允许因一人四翼而无条件把总预算翻倍。

大量玩家同时攻击时先减墨屑，再降低远端管径截面/细流/轴向精度，始终保留每名相关攻击者的主轴方向和落点表达。动画时钟始终逐帧推进，第一批不以“隔几 tick 更新一次网格”作为降负载手段，避免变相恢复顿挫。若仍需降低几何更新频率，必须同时实现端点/姿态插值，再单独验收。

## 7. 网络接收者与飞行控制

攻击广播改为“本人 + 已追踪该角色、在效果兴趣范围内的观察者”，去重发送。开始追踪时补必要状态。第一批保持 128 米范围上限，不因降低 LOD 缩小攻击事件覆盖；效果落点延伸需计入范围，边缘相关观察者不能只按角色中心剔除。

NeoForge 官方文档提供按追踪对象分发的方向，但目前公开页面版本为 26.1，本项目为 26.2 且使用 Misaka 包封装；具体 API 以项目实际依赖源码和编译结果为准，不直接照搬示例替换网络层。[官方载荷文档](https://docs.neoforged.net/docs/networking/payload/)

飞行控制按两个可单独验证的步骤实施：

1. 合并方向位和姿态角，一 tick 最多一个输入包。服务端保存输入意图，在服务端玩家 tick 中统一施加一次运动，按现有前后/左右顺序合成，保持斜向、垂直、加速、KEEP 阻尼手感。回发速度先限制为每 tick 一次。服务端包处理只更新输入，不立即推玩家。
2. 对已保存的输入采用“按键变化立即发、朝向变化超过阈值发、保持状态每 4 tick 心跳”；变化频繁时封顶 20 包/秒。初始朝向阈值约 1°，经过轨迹误差测试调整。服务端每 tick 继续计算运动；初始 10 tick 未收到输入进入安全 KEEP，禁止在断流后持续 BOOST。输入恢复按序号接续。只有验证足够稳定后，速度纠正再采用误差阈值和保底心跳。

该设计降低保持输入时的包数量，并限制包突发导致的额外推力。不能只把现有 `clientTick` 改为每 4 tick 调用，因为当前移动量和阻尼依赖收包次数。

共享 `WingFlightSupport` 会影响白翼、白金翼等技能，飞行网络改动应独立于黑翼画面修复交付，并复测共享调用方。若已有 API 适合抽象输入意图/运动推进，应复用；否则把通用推进能力抽成可公开调用的接口，具体技能只提供参数与授权，避免继续增加私有复制实现。

## 8. GPU 升级路径与适用条件

如果完成上述采样、内存和预算修复仍达不到多人性能目标，再增加参数化风暴输出：静态模板保存轴向 u、环角和细流 ID，每帧仅上传分支主轴/旋转/包络、时间和材质参数，由顶点着色器完成细流偏移与世界变换。高光依附同一表面坐标，镂空保留真实可见空隙和桥接关系。编辑器与游戏调用相同输出节点；CPU 路径作为回归对照和兼容回退。

先做一个分支原型，核实当前渲染抽象可传入的顶点属性、uniform/UBO 容量和实际 GPU 限制，再扩到双翼/四翼。当前着色器是 GLSL 330，方案不要求直接升级到 compute shader 或 SSBO。不能把所有原本重复的复杂计算简单搬到每一个 GPU 顶点上，否则只是转移瓶颈。

动态 GPU 数据使用当前渲染设备提供的安全分帧缓冲机制；是否使用多缓冲和同步栅栏由后端能力决定。OpenGL 对仍在被 GPU 使用的缓冲进行改写可能触发隐式等待；持久映射另有版本/扩展与同步要求。因此不直接添加裸 `UNSYNCHRONIZED` 映射绕过安全检查。[Khronos 缓冲流式更新说明](https://wikis.khronos.org/opengl/Buffer_Object_Streaming)

该阶段单独检查透明叠层开销。改变核心深度写入、混合模式或大面积改成 billboard 都会影响外观，必须有前后对照证据后再决定，不能作为未经验证的默认修复。

## 9. 验证矩阵与验收门槛

### 9.1 必要观测

开发诊断按固定时间窗口汇总，不逐帧刷日志：

- 客户端：总帧时间 P50/P95/P99；黑翼曲线采样、建网格、复制/上传分项；活跃/可见/各 LOD 人数；曲线/顶点/上传量；堆与直接内存分配、GC 停顿。
- 事件：收到、接受、重复、等待实体、合并、过期、取消数量；网络入口到主线程处理的排队时间；处理到首次画面的时间；本机输入到首次画面的时间。
- 服务端：TPS/MSPT、黑翼目标查询/伤害/控制推进耗时、按类型收发包数和字节数。区分 RTT、服务端排队和客户端排队，跨端时钟没有校准时不记录伪精确“单向延迟”。
- GPU：在实际客户端用 RenderDoc 或可用的时间查询检查上传等待、顶点与透明片元负担。采样工具关闭后再记录最终性能。

### 9.2 自动化与视觉回归

- 时间线纯逻辑测试：时钟偏移 ±40 tick、重复/旧序号、关闭重开周期、实体晚到、暂停恢复、10 秒以上无效历史包、多包同帧、世界切换、当前+待播容量、迟到有效事件首次播放、连招正常顺序。
- 网络测试：新 codec 往返和边界输入；同一请求只扣费/伤害一次；追踪开始/结束；四个落点精确保持；可选预测确认不重播、拒绝不改变服务端状态。
- 采样回归：现有五招路径、挥动先后、四角高度、目标方向、无 NaN、起末连续恢复；优化前后关键点偏差先控制在 0.01 m 内，关键姿态端点保持现有测试精度。近景截图对比左右高光、细带粗细、移动小孔和黑转白过渡。
- 预算回归：0/1/8/16 个效果总量不越界，四翼突发也受限；视野外跳过昂贵求值；屏幕边缘只见翼尖时仍显示；往返边界不反复分配，不重置相位；低 LOD 保留所有相关攻击的基本方向。
- 内存检查：固定效果数预热后大型直接缓冲分配停止；10 分钟反复进入视野/切换五招/重载资源后无持续增长，资源关闭全部释放。
- 飞行回归：各方向、斜向、加速、松键、开 GUI、输入断流与恢复，20 tick/s 同输入轨迹与原实现保持一致；包发送频率变化不改变速度，突发重复包不额外加速；白翼/白金翼相关路径不回归。

### 9.3 联机测试场景

使用独立服务器和多个真实客户端，至少 2/4/8 人，16 人作为压力档；仅生成测试实体可测几何压力，不能替代多人网络验收。

分别测试全员待机、全员正常连招、同步四翼峰值、边飞边打；全部近处与近中远混合；相机快速转向、第一/第三人称、只露出翼尖、黑转白、晚加入/切维度。

网络条件覆盖 RTT 0/100/200/400 ms，抖动 0/50/100 ms，受限吞吐，以及 0.8–2 秒短时断流。传输层丢包按可靠连接的重传/队头阻塞观察，不把它当成每个自定义事件会独立丢失的 UDP 场景。另用事件队列注入测试重复/旧消息和实体状态顺序。测试前记录带宽设置、方向、RTT 与实际观测值。

### 9.4 建议验收目标（待实施后测量）

| 项目 | 目标 |
| --- | --- |
| 连续播放 | 服务器接受且未被更新事件取代的有效事件，不再因为跨端 tick 差而零帧消失；重复事件不重播 |
| 时长与手感 | 正常运行 0.8 秒，误差不超过一帧；蓄势约 20%，没有确认包造成的中段停顿；高延迟观察者允许晚开始但开始后连续 |
| 普通联机 | RTT ≤400 ms、抖动 ≤100 ms、客户端帧率 ≥30 FPS、服务器接近 20 TPS 时，持续轮换不发生由播放规则导致的整招漏播；异常断流按有界恢复策略计数 |
| 多人几何 | 8 人场景遵守 120,000 顶点与 8 MiB/帧初始预算；相关攻击主轴/落点仍可见，本机保留批准近景 |
| CPU | 同一台 i9-14900KF 上，8 人混合距离正常连招的黑翼 CPU 总耗时 P95 目标 ≤4 ms；单人四翼采样中位目标 ≤2 ms。二者是验收目标，不是当前结果 |
| 内存 | 固定场景预热后不按曲线/帧创建大型直接缓冲；整体分配率相对基线降低至少 80%，无随时间累计增长 |
| 输入网络 | 保持同一方向时控制输入约 5 包/秒；快速变化最多 20 包/秒；先确保运动轨迹一致再启用降频 |
| GPU | 记录 RTX 5070 Ti 在固定 1080p、相同场景设置下黑翼增量 GPU 耗时与帧时间；以实测瓶颈决定是否进入 GPU 升级，不预先宣称 FPS 提升幅度 |

实施后按仓库要求依次运行 `./gradlew test -DisDev=true`、`./gradlew build -DisDev=true`、`./gradlew build -DisDev=false`，再通过 `runClientDev` 及独立服务器进行上述联机/视觉检查。离屏图、单测和编译通过不等于联机验收通过。

## 10. 实施顺序与交付边界

| 批次 | 交付内容 | 完成条件 |
| --- | --- | --- |
| A：诊断与播放 | 轻量计数器；激活周期/序号；本地时间线；实体等待；有界队列；停用清理 | 延迟、时钟偏移、突发事件测试通过；游戏中迟到攻击可开始并连续播放 |
| B：渲染成本 | 主轴缓存、直接写合并缓冲、正确包围范围和剔除、动态 LOD/全局预算 | 保留近景外观；达到分配和几何预算目标；2/4/8 人实测 |
| C：网络与飞行 | 追踪接收者；输入合并、服务端 tick 推进，再开启变化发送/心跳 | 同输入轨迹一致；共享羽翼回归通过；受限带宽复测 |
| D：按指标升级 | 本机视觉预测用于剩余输入等待；GPU 参数化输出用于剩余 CPU/上传瓶颈 | 各自有开关和回退；分别验证预测一致性、画面一致性和实测收益 |

A、B 是本次问题的必做主体；C 解决额外网络压力并与画面修复分开验证；D 由 A–C 的实测决定是否需要，不把大规模渲染重写作为开始修复的前置条件。

任何批次都先完成对应验证再交付，只有用户明确要求时才创建中文本地 Git 提交。当前代码与测试结果见实施结果文档；真实多人限速网络及 GPU 性能验收尚未完成。
