# `api` 与 `internal` 边界约定

## 1. 目的

本文定义 AcademyCraft-Reborn 源码中 `org.academy.api` 与 `org.academy.internal` 的归属和使用边界。

这里的 `api` 不是“永远稳定的接口”的同义词，也不承诺版本间兼容。它表示：该功能被项目明确整理为**外部合规使用面**，其它 MOD、附属 MOD 或其它独立模块可以按其公开语义使用，即使未来仍可能调整、重命名或移除。

`internal` 表示：该功能不是外部合规使用面，只服务于本 MOD 的实现。外部代码技术上可能通过类路径、反射或其它方式强行使用它，但这种使用属于 hack，不属于项目支持或认可的行为，项目不会主动为此设置限制，也不保证其行为或存在性。

## 2. 两种归属的含义

### `api`

放入 `api` 的功能满足以下语义：

- 项目愿意把它作为外部可合规使用的能力；
- 外部调用方可以依据其公开类型、方法和行为意图使用它；
- 它不要求承诺永久稳定，也不自动形成兼容性保证；
- 它可以包含实现、状态和运行时逻辑，不要求一定是 Java interface、抽象类或纯数据契约；
- 类名中出现 `Manager`、`Runtime`、`Renderer`、`Client` 等实现色彩，不足以证明它应归入 `internal`。

因此，`api` 的判断重点是“是否被整理为外部合规使用面”，而不是“是否是接口”或“当前是否已有外部调用者”。

### `internal`

放入 `internal` 的功能满足以下语义：

- 外部不应依赖它；
- 它是本 MOD 的实现细节、状态管理、生命周期管理、事件处理、Mixin 配合代码、内部算法或技能专用逻辑；
- 外部强行使用它不一定会被阻止，但该行为是不合规的 hack；
- 它可以随时变化、移动、删除或改变行为，不需要为外部 hack 保持兼容。

## 3. 判定方法

对每个功能先问：

> 我们是否愿意把这个功能整理并声明为附属 MOD 或其它外部模块可以合规使用的能力？

- 愿意：归入 `api`，并按外部调用场景设计公开类型、线程要求、生命周期和失败行为；
- 不愿意：归入 `internal`，外部使用只能视为 hack；
- 尚未决定：先保留在当前归属，记录为待决项，不通过机械移动来预先表达公开承诺。

“本仓库里有没有外部引用”不能作为主要证据。模组本体天然缺少真实外部消费者；应该根据预期外部使用语义判断。

同时，不应仅凭以下因素做归属决定：

- 类名是否像实现类；
- 当前是否只有本 MOD 使用；
- 是否存在 `package-info.java`；
- 官方文档或旧规划是否曾把某个包称为公开包。

## 4. 依赖方向

`api` 与 `internal` 的依赖方向应服从以下原则：

- `api` 不应直接依赖 `internal` 或 `mixin`，因为这会把内部实现细节泄漏到外部合规使用面；
- `internal` 可以依赖 `api`，因为内部实现可以使用项目公开的合规能力；
- 如果一个功能应归入 `api`，但其实现严重依赖 `internal`，不能通过简单移动文件解决；应重新设计功能边界、公开数据类型和生命周期，再分阶段迁移；
- 如果一个门面只是本 MOD 内部调用的转发层，且没有外部合规语义，可以删除门面并让调用方直接使用 `internal`；
- 如果一个门面确实代表外部合规能力，则应先确认其公开语义，再决定哪些实现、状态和事件属于 `api`，哪些继续属于 `internal`。不得为了满足目录形式而机械搬运整个实现依赖链。

## 5. Bridge、Backend 与类似机制

`Bridge`、`Backend`、`Provider` 这些名称本身不决定归属，也不自动构成违规。

判断重点是：

- 它是否只是本 MOD 内部实现之间的临时转发层；
- 它是否把一个本应明确划界的公开能力隐藏在不清晰的注入机制后；
- 它是否让 `api` 暴露了外部不应实现的内部生命周期或实现细节；
- 它是否确实用于支持合规外部扩展或可替换实现。

对于复杂功能，应先做功能归属和依赖边界设计，再决定保留、删除或替换这类机制。禁止把“删除所有 `Backend`/`Bridge`”当作不经分析的全局重构规则。

## 6. 迁移要求

从 `internal` 迁移到 `api` 不代表简单改包名，而代表对外合规使用面的重新承诺。迁移前应明确：

- 外部调用者的使用场景；
- 可见参数、返回值和事件类型；
- 线程、客户端/服务端和生命周期要求；
- 失败、未初始化和版本变化行为；
- 哪些状态和实现细节仍然属于 `internal`；
- 现有内部调用方如何逐步迁移；
- 测试如何验证公开语义，而不是只验证当前实现类名或路径。

复杂功能应按功能分组逐步迁移。每组先完成归属与契约设计，再迁移实现和调用方，最后运行 api/internal 依赖检查与相关测试。

## 7. 一句话总结

`api` 表示“外部可以合规使用，但不承诺永久稳定”；`internal` 表示“外部不应使用，强行使用属于 hack，项目不主动限制但不负责兼容”。
